# Workflow-Driven Module Settings — Proposal & Assessment

> Status: **parked for review**. Idea: every module's Settings tab should be
> generated by the Workflow form builder, with a live workflow definition
> running behind each settings form, so end users can define custom workflows
> per module without code changes.

## Where the POC already points this way

`src/features/workflows/components/engine-artifacts-panel.tsx` implements
"Layer 3 — Consume": a module's configuration is not owned by the module — it
is the Workflow Engine catalog filtered to artifacts targeting that module
(authored once in the engine, toggled per scope, consumed in the module's
Admin tab). This proposal extends that from *which capabilities are on* to
*the settings forms themselves*.

## Pros

- **One source of truth, zero drift.** Every module's settings UI comes from
  one builder and one renderer. UI-inconsistency bugs (like the Directory
  table vs. SimpleTable divergence) become impossible for settings forms —
  there is only one form engine to fix.
- **Per-tenant customization without deploys.** In the portfolio → group →
  company hierarchy, each tenant can extend a settings form (extra fields,
  extra approval step) as data, not code. This is the core promise of a
  multi-tenant HRMS — Kensium's custom fields and approval matrices already
  point this way.
- **Config changes become governed events.** If a settings save is itself a
  workflow instance, you get approval-on-config-change (e.g., changing leave
  accrual rules requires HR director sign-off), a free audit trail, effective
  dating, and rollback — standard enterprise HR buyer asks.
- **RBAC enforced in one place.** Scope rules (who can edit what, at which
  level) live in the engine instead of being re-implemented slightly
  differently across every module's Admin tab.
- **New setting = new artifact.** Platform admin publishes a form + workflow
  to all tenants; no frontend release needed.

## Cons

- **The inner-platform effect.** You end up building a low-code platform
  inside the HRMS. Real settings need conditional visibility, cross-field
  validation, rule grids (approval matrices, accrual bands) — the form
  builder gradually has to reinvent everything React already provides, but
  worse.
- **Type safety evaporates.** Settings stop being typed config objects and
  become schema-driven blobs. Consuming modules must defensively parse them;
  when a workflow output shape changes, the compiler catches nothing
  downstream.
- **Debugging moves from code to data.** A bug is no longer a stack trace;
  it's a misconfigured definition in some tenant's workflow. Requires
  instance tracing, definition versioning, and a dry-run/simulation mode.
- **Versioning burden.** Running instances pinned to old definition versions,
  migrations for stored form data, tenants on divergent versions of the
  "same" form — real ongoing cost.
- **UX ceiling.** Generated forms are serviceable but rarely great for
  complex settings (shift patterns, accrual grids). An escape hatch for
  hand-built widgets is needed — and once it exists, teams overuse it.
- **Guardrails needed.** End users can author broken workflows — approval
  cycles, unreachable approvers, dead ends. The builder must validate and
  simulate before publish.
- **Bootstrap problem.** The engine's own settings can't be engine-generated;
  some config always stays in code.

## Recommendation — hybrid

1. **Keep the engine as the owner of *which* capabilities are on per scope**
   (the current `EngineArtifactsPanel` pattern).
2. **Move *policy-like* settings into form-builder artifacts** — approval
   chains, notification rules, eligibility criteria, SLAs. These are exactly
   the settings tenants want to customize, they are naturally rule-shaped,
   and they benefit most from audit/approval semantics.
3. **Keep *structural/complex* settings as hand-built forms** that read and
   write engine artifacts underneath — single source of truth without capping
   the UX.

## Suggested POC demo (when picked up)

One module end-to-end — e.g., **Leave approval rules**:
design the form in the Workflow builder → publish → the Leave module's
Settings tab renders it → a settings change spawns an approval workflow
instance visible in the engine's Instances tab.
